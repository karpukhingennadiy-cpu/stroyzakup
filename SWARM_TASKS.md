# БЛОК A. ПОЛНОЕ ТЕСТИРОВАНИЕ (QA)

## A1. Тест-матрица пользовательских сценариев (E2E, браузер)
**Цель:** пройти все пути UI и зафиксировать дефекты.
**Контекст:** frontend/app/lk/requests/new/page.tsx (мастер 3 шага), /quote/[token], /lk/requests/[id]/competitive.
**Сценарии:**
1. Регистрация нового пользователя → логин → выход → повторный логин.
2. Создание заявки: 1 позиция / 5 позиций / позиция без количества / текст мусором («asdf 123»).
3. Парсинг: позиции с низким confidence — видны ли уточняющие вопросы; редактирование позиции через update_item.
4. Адрес: клик по карте / ввод города текстом / отказ без адреса (кнопка disabled).
5. Подбор: фильтр «только производители», раскрытие score_breakdown, выбор 0/1/всех поставщиков.
6. RFQ: отправка → статус rfq_sent; повторная отправка тем же — создаются ли дубли писем (не должны критично ломать).
7. КП: открыть /quote/{token} из письма (token в БД RfqInvitation), заполнить, отправить, переоткрыть — данные сохранились.
8. Конкурентный лист после 2+ КП от разных поставщиков.
9. Истёкшая сессия: удалить access_token из localStorage → действие → редирект на /login.
10. Мобильная ширина (375px): мастер заявки и таблица поставщиков.
**Приёмка:** протокол «сценарий → ожидание → факт → статус PASS/FAIL + скриншот» в файл `docs/QA_E2E_PROTOCOL.md`. Все FAIL заведены как задачи.

## A2. API-тесты: покрытие негативных веток
**Цель:** дополнить tests/ негативными сценариями до 45+ тестов.
**Файлы:** backend/tests/test_requests.py, test_matching.py, test_quotes.py, test_suppliers.py.
**Задачи:**
- parse для чужой заявки (404/403), parse пустого raw_text, parse повторный (diff-update, позиции не дублируются).
- match_suppliers без адреса, match с лимитом 5.
- send_rfq: пустой supplier_ids (400), несуществующие id, поставщик без email (skipped), повторная отправка.
- public_quote: невалидный токен (404), POST с ценой 0/отрицательной, POST без позиций, throttle 30/мин (31-й запрос → 429).
- competitive_sheet без request_id (400), с несуществующим id.
- geocode: пустой адрес, несуществующий адрес.
**Приёмка:** pytest 45+/45+ зелёный, время прогона < 3 мин (LLM-вызовы мокать, не вызывать реальный API).

## A3. Нагрузочный sanity-тест
**Цель:** убедиться, что синхронная обработка не деградирует.
**Шаги:** locust или скрипт на httpx: 20 параллельных созданий заявки; 10 параллельных match_suppliers по одной заявке; замер p50/p95.
**Приёмка:** отчёт в docs/QA_LOAD.md; p95 создания < 3с (без LLM — мок), p95 подбора < 5с; нет 500-х; нет дедлоков SQLite (если есть — зафиксировать как аргумент для PostgreSQL).

## A4. Тест граничных данных
**Цель:** устойчивость парсера и матчера.
**Набор:** 20 реальных формулировок закупок (опечатки «бурсчатка», латиница «bruschatka», «куб бетона», «пачка гипсокартона», единицы «куб.м», «м2», «штук»).
**Приёмка:** таблица «вход → категория/material_type → корректно?» в docs/QA_PARSE_MATRIX.md; точность категоризации ≥ 85%; провалы — задачи на доработку словарей/parser.py.

## A5. Проверка email-контура
**Цель:** письма читаемы в реальных клиентах.
**Шаги:** отправить RFQ на тестовый ящик (Gmail + Mail.ru); проверить: HTML-таблица позиций, кнопка «Заполнить КП» ведёт на рабочий URL, кириллица в теме, reply-to rfq-XXX@in.минитендер.рф.
**Приёмка:** скриншоты письма в 2 клиентах; ссылка /quote/{token} открывается; отмечено, что для prod нужен публичный FRONTEND_URL (сейчас localhost).

## A6. Безопасность (базовый аудит)

**Приёмка:** docs/QA_SECURITY.md со списком находок; критичные закрыты кодом.

# БЛОК B. ЗАВЕРШЕНИЕ РАЗРАБОТКИ (фичи prod-уровня)

## B1. Приём ответов поставщиков по email (inbound)
**Цель:** письмо-ответ на rfq-XXX@in.минитендер.рф автоматически создаёт КП.
**Контекст:** apps/emails/services.py::process_inbound_email_reply (логика есть), нет транспорта.
**Шаги:**
1. MX-запись in.минитендер.рф → сервер приёма (инструкция в docs/INBOUND_SETUP.md).
2. Вариант транспорта: polling IMAP-ящика по расписанию (management command `fetch_inbound`) — проще, чем SMTP-сервер.
3. Парсинг тела: LLM извлекает цены из текста письма → Quote + QuoteItem (по аналогии с parser.py).
4. Тест: реальное письмо-ответ → КП в конкурентном листе.
**Приёмка:** end-to-end: отправка RFQ → ответ письмом → КП в системе; fallback: кнопка «внести КП вручную» уже есть.

## B2. Асинхронность (Celery + Redis)
**Цель:** убрать синхронные ожидания (парсинг до 60с, discovery до 60с).
**Контекст:** apps/requests/tasks.py и apps/emails/tasks.py готовы, views работают синхронно (помечено «Sync-only in dev»).
**Шаги:** поднять Redis (docker-compose есть), переключить views на .delay(), фронт — polling статуса заявки (draft→parsing→confirmed) с прогресс-индикатором.
**Приёмка:** parse/match/send_rfq возвращают 202 + task_id; UI показывает прогресс; синхронный fallback сохраняется по флагу USE_CELERY=false.

## B3. PostgreSQL в prod-контуре
**Контекст:** docker-compose.prod.yml, config/settings/prod.py, psycopg2 уже в зависимостях.
**Шаги:** поднять postgres контейнер, миграции, перенос демо-данных (dumpdata/loaddata), прогон тестов на PG (через env DATABASE_URL).
**Приёмка:** весь цикл на PostgreSQL; SQLite остаётся для dev.

## B4. Модерация поставщиков
**Цель:** source=llm поставщики не попадают в подбор до проверки.
**Контекст:** Supplier.moderation_status (unverified/verified/rejected) существует, в матчере не фильтруется.
**Шаги:** матчер — фильтр moderation_status != rejected + понижающий коэффициент для unverified; страница /lk/suppliers — кнопки подтвердить/отклонить (роль staff); админ-эндпоинт bulk-verify.
**Приёмка:** отклонённый поставщик исчезает из подбора; unverified помечен в UI.

## B5. Ручное добавление поставщика
**Шаги:** форма в /lk/suppliers (название, email, город, категории, тип) → POST /suppliers/ (эндпоинт есть — проверить) → автообогащение через fill_supplier_catalog + геокодинг.
**Приёмка:** добавленный вручную поставщик участвует в подборе в течение минуты.

## B9. LLM-переписка с поставщиками: библиотека промтов
**Цель:** система сама ведёт деловую переписку по тендеру — составляет письма и отвечает поставщикам через DeepSeek, в едином деловом стиле и без выдуманных фактов.
**Контекст:** apps/emails/services.py (текущие статичные шаблоны RFQ_TEMPLATE_*), apps/emails/services.py::process_inbound_email_reply (входящие), apps/requests/services/material_intel.py (образец LLM-сервиса с кэшем).
**Шаги:**
1. **Промт-библиотека** `apps/emails/prompts.py` — отдельный промт на каждый сценарий:
   - приглашение в тендер (RFQ) — генерация текста под конкретного поставщика и заявку;
   - напоминание о дедлайне (за 24ч и за 2ч до срока);
   - уточняющий вопрос поставщику (неясная цена/аналог/условия в его КП);
   - ответ на вопрос поставщика по условиям заявки (только из данных заявки!);
   - благодарность за КП + подтверждение получения;
   - уведомление о победе / вежливый отказ остальным.
2. **Правила безопасности промтов (жёстко в system-промте):**
   - не обещать цены, скидки и объёмы от имени заказчика;
   - не выдумывать условия — только факты из заявки (позиции, адрес, срок);
   - тон: деловой русский, коротко, без канцелярита;
   - подпись «команда Минитендер.рф», без имён людей;
   - любые обещания/контрагентские формулировки → эскалация человеку (пометка needs_review, письмо не отправляется).
3. **Сервис** `apps/emails/llm_writer.py`: вход (сценарий, заявка, поставщик, контекст переписки) → JSON {subject, body_text, body_html, needs_review}; кэш по хэшу контекста; fallback на статичные шаблоны при недоступности LLM (текущее поведение).
4. **Интеграция:** send_rfq использует llm_writer; inbound-ответы (B1) анализируются LLM и, если это вопрос, а не цены, — генерируется ответ-разъяснение.
5. **Eval-набор промтов:** 15 эталонных сценариев в backend/tests/test_llm_writer.py — мок LLM, проверка: структура JSON валидна, запрещённые формулировки отсутствуют («гарантируем», «скидка», «оплатим»), факты совпадают с заявкой; needs_review срабатывает на провокационных входных («дай скидку 30% и мы подпишем»).
**Приёмка:** RFQ-письмо генерируется LLM и содержит только факты заявки; при сбое LLM уходит статичный шаблон; eval-тесты зелёные; письмо с needs_review НЕ отправляется и видно в админке.

## B10. Напоминания поставщикам по дедлайну
**Цель:** scheduled-задача (management command по cron / Celery beat): за 24ч и за 2ч до срока — напоминание всем, кто не ответил (текст — из llm_writer, сценарий «напоминание»).
**Приёмка:** тестовый запуск команды создаёт письма только неответившим; повторный запуск не дублирует напоминания.
